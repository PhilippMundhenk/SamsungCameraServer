CLAUDE
[web searches: Samsung NX1000 wifi reverse engineering; samsung-nx-emailservice]
Good news: most of the reverse engineering is already done. The camera's WiFi
features are plain HTTP/SOAP/UPnP, unencrypted, and the community has
documented them.

1. PC Auto Backup (best for originals) — camera on your home WiFi pushes
   full-size files to a "PC". There's a complete reimplementation of
   PC-Autobackup in Python for Linux and Mac, linked from the samsung-nx-hacks
   wiki (https://github.com/ge0rg/samsung-nx-hacks/wiki/PC-Auto-Backup). Run
   it on your Proxmox/NAS; the feature matrix confirms NX1000/NX1100 support
   PC Auto-Backup.
2. Email/social upload -> self-hosted server — the web services were
   discontinued around January 2021, but there's a Flask-based
   reimplementation you can self-host after redirecting DNS:
   https://github.com/ge0rg/samsung-nx-emailservice. It can send emails, post
   to Mastodon, or store to a directory on the server; you point
   gld.samsungosp.com, www.samsungimaging.com, www.ospserver.net and
   snsgw.samsungmobile.com at it — trivially done with Unbound host overrides
   on your OPNsense. Caveat: email mode downsizes images.
3. MobileLink / Remote Viewfinder (Wi-Fi Direct to phone) — the old Samsung
   Smart Camera App APK still installs on Android (APKMirror) and works offline
   since the camera is the AP. Remote Viewfinder (SOAP, HTTP stream) is
   documented on the wiki; MobileLink is UPnP-based and less documented — this
   is the one spot where a reimplementation would be new work.

Reverse engineering yourself: easy. Make a Linux box the AP (hostapd) or
mirror the camera's port on OPNsense, run Wireshark/mitmproxy — it's all
cleartext XML. Note the NX1000 is a DRIMeIII camera, not Linux-based like the
NX300, so on-camera hacks are out; everything has to be emulated on the peer
side.

Zero-effort fallback: an ezShare WiFi SD card bypasses the camera's WiFi
entirely.

Sources: samsung-nx-hacks (https://github.com/ge0rg/samsung-nx-hacks/), wiki
(https://github.com/ge0rg/samsung-nx-hacks/wiki), samsung-nx-emailservice
(https://github.com/ge0rg/samsung-nx-emailservice)

USER (13:46)
Is auto backup supported? Camera has an auto backup menu but tells me to
connect via USB. How does this work?

CLAUDE
[web searches: PC Auto Backup USB registration; found n-i-x/pc-autobackup]
Yes, NX1000 is explicitly on the tested list. The USB step is just a
registration trick, not a transport.

How the original worked: the Windows PC Auto Backup tool used the USB
connection only to write a small config onto the camera's SD card containing
the PC's hostname and MAC address (so the camera "knows" which PC it's paired
with and can send WoL). On WiFi, the camera then does UPnP/SSDP discovery,
matches the registered PC, and uploads originals over HTTP/SOAP. The USB-mount
step is therefore replaceable by writing that file yourself.

The reimplementation: https://github.com/n-i-x/pc-autobackup (Linux/macOS).
Workflow: mount the SD card in a reader, run
pc_autobackup.py --create_camera_config=/path/to/sdcard (or
--import_camera_config if it was ever paired with the Windows tool), put the
card back, then run pc_autobackup.py as the server on your LAN. The camera's
Auto Backup menu then finds it instead of asking for USB.

Caveats:
- The repo was archived in May 2023 and targets Python 2.7 — expect to port
  it to Python 3 (small codebase; a quick Claude Code job) or run it in a py2
  container.
- Camera and server need to be on the same L2 segment (SSDP multicast) —
  watch your OPNsense VLANs/AP isolation.
- It's known to be firewall-sensitive (UDP 1900 + the TCP port the server
  announces).

USER (13:58)
So essentially the camera gets a wifi config written to SD card? Then
connects to a server, correct?

CLAUDE
Almost, with one correction: the file on the SD card is not a WiFi config,
it's a pairing record — the backup PC's name and MAC address (that's what the
Windows tool wrote over USB). The WiFi network itself is configured in the
camera's own menu as usual.
Flow:
1. SD card: write the pairing record (--create_camera_config).
2. Camera: select Auto Backup -> it joins your home WiFi (saved network or
   you pick one).
3. Camera sends a Wake-on-LAN magic packet to the paired MAC, then does an
   SSDP/UPnP discovery on the LAN.
4. Your server answers the discovery, advertising the matching name/MAC.
5. Camera uploads new files over HTTP/SOAP; the server tracks what's already
   backed up.
So the server must run on the host whose MAC is in the pairing record (or at
least advertise that MAC in its UPnP description — pc-autobackup lets you set
it), and it must sit on the same L2 segment as the camera for the multicast
discovery to work.

USER (14:03)
Analyze the file format: What's exactly needs to be written to the cameras

CLAUDE
[cloned n-i-x/pc-autobackup, read common.py, pc_autobackup.py, mediaserver.py]
Analyzed the source. The pairing file is tiny and fully static — exactly what
we hoped.

Path on the SD card (NX1000): dlna_web_root/SAMSUNGAutoBackupDESC.ini (the
Windows tool created that folder; our server bundle just includes it). The
model is read from SYSTEM/DEVICE.XML on the card, but only to pick the
path/case for the filename.

Contents (CRLF line endings, 5 lines):
    MacAddr=AA:BB:CC:DD:EE:FF
    UDN=uuid:4a682b0b-0361-dbae-6155-xxxxxxxxxxxx
    friendlyName=[PC]AutoBackup
    WOLSupport=1
    ServerFlag=1

What each field does:
- UDN — the only thing the camera actually matches. It must equal the UUID in
  the server's SSDP USN header and UPnP device description. The first four
  groups are a fixed Samsung prefix; only the last 12 hex digits vary.
- friendlyName — shown on the camera, also in the device description.
  Cosmetic match.
- MacAddr — used only for the Wake-on-LAN packet. The server never advertises
  it; with an always-on server it's irrelevant (can be any value).
- WOLSupport / ServerFlag — constant 1.

Implication for the design: the server picks one UUID + name at install,
bakes them into this file, and that file is identical for every camera,
forever. No per-camera data, no USB, no WebUSB needed. The web UI just serves
a zip containing dlna_web_root/SAMSUNGAutoBackupDESC.ini; the user unzips to
the card root. Even the --import path becomes trivial: a card paired with the
old Windows tool just needs its UDN copied into the server config.

The protocol side is equally small: SSDP M-SEARCH responder for
MediaServer:1, one device-description XML, and three SOAP actions —
X_BACKUP_START, CreateObject (returns an import URI), the HTTP POST upload to
that URI, and X_BACKUP_DONE.

Ready to scaffold the Python 3 server on that basis?

Pairing file — final spec. Keys: MacAddr=, UDN=, friendlyName=, WOLSupport,
ServerFlag=1. Nothing else; the loop has no other key strings. MacAddr and
UDN are required (missing -> "no MacAddr!!" / "no UDN!" error), friendlyName

the SSDP device list ("Appear Target DMS... UDN: %s") — no serial involved,

Dedup — answered properly now. The camera keeps a SQLite DB on the card at
config/DMC/MSCP/mscp.db, table ObjectTable with an IsBackup column; backup
candidates are `select FullPath ... where IsBackup != 1`. So: per-card,
survives power cycles, resets on format. Since it's plain SQLite on FAT, the
server bundle could even ship a tool to reset or seed it.

Bonus hooks found:
- CreateObject "File Exist" error path: if the server answers with the right
  UPnP error, the camera skips the file and moves on — server-side dedup that
  the camera respects.
- Resumable uploads: the camera handles ImportURI + UploadedSize/start
  offset, so interrupted hotspot transfers can resume.
- X_BACKUP_DONE carries a SysOff flag — the camera's "shut down PC after
  backup" option. We can map it to anything (trigger photosort, send a

- SSDP TTL is 2, so a single routed hop would work if your OPNsense relays
  multicast; same-L2 is still simplest.
